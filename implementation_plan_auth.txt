# FitFreak - Google Authentication + Vitals Onboarding

Status: not started (written 2026-11-13).
Work through the phases in order. Phases 2 and 4 can run in parallel (backend vs app).
Phase 7 must come last - it needs a real signed-in account to exist first.
Tick the [ ] boxes as work lands; each phase ends with a "Done when" check.


## Goal

- Sign in with Google. No email/password, no other providers.
- After a first successful sign-in, a one-time onboarding flow captures the user's vitals
  (age, sex, height, weight, activity level, goal, diet) before the app proper opens.
- Every existing endpoint becomes genuinely per-user instead of hard-coded 'default_user'.
- The 220 workouts already in the database (2026-04-25 -> 2026-10-29) end up owned by your
  own Google account, not lost and not claimable by a stranger.


## Starting point

Good news: the data layer is already user-scoped. The work is replacing a stub, not
retrofitting a concept.

- backend/middleware/auth.js is a 4-line stub: it sets `req.userId = 'default_user'` and
  calls next(). It is mounted globally in server.js via `app.use(auth)`.
- Every controller already reads `req.userId`, and every user-owned model already has a
  `userId` field (CompletedWorkout, TargetMuscle, CustomExercise). They all carry
  `default: 'default_user'` and every controller has a `|| 'default_user'` fallback.
- backend/models/Exercise.js is a global seeded catalog with no userId. It stays global.
- The app has no login, no user object and no token handling. src/services/api.ts talks to
  the backend with bare `fetch` and no headers.
- src/core/AppHeader.tsx greets a hard-coded "Hi Mukul".
- Offline-first writes: src/store/syncStore.ts queues every mutation (persisted to
  AsyncStorage) and drains it on reconnect. A queued request can sit for days.
- historyStore and activeWorkoutStore persist to AsyncStorage with no user in the key.
- The project is managed / CNG - there is no android/ or ios/ directory. Current testing is
  Expo Go + `npx expo export`. eas.json has preview / development / production profiles;
  the development profile has `developmentClient: true` but no `env` block.

Hard constraint discovered while researching this plan:

- Native Google Sign-In CANNOT run in Expo Go. Expo's own guide (docs.expo.dev/guides/
  google-authentication/, updated 2026-11-02) lists only @react-native-google-signin/
  google-signin and react-native-nitro-google-signin, and states both require custom native
  code, a config plugin and a development build. The old expo-auth-session Google provider
  is marked deprecated in Expo's AuthSession docs, which now point at the native library
  instead.
- So Phase 1 is "get a development build onto the phone". From this phase on, Expo Go is no
  longer the test target for anything touching auth. Everything that does not touch auth
  still works in Expo Go as long as you guard the import (see Phase 1 notes).

Things that will bite if not handled deliberately (each has a step below):

- syncStore treats any non-ok response as permanent and DROPS the request after logging
  (`// We reached the server, so retrying won't help`). Once auth exists, an expired token
  returns 401 - which would silently discard finished workouts. Must special-case 401.
- `CompletedWorkout.id` is `unique: true` globally. With more than one user that uniqueness
  belongs to the pair (userId, id), not to id alone.
- The `|| 'default_user'` fallbacks must go. If the middleware ever fails open, those
  fallbacks quietly merge every user's data into one bucket instead of erroring.
- historyStore / activeWorkoutStore AsyncStorage caches are not user-scoped, so signing out
  and signing in as someone else on the same phone would show the previous user's history.


## Decisions

| Topic                  | Decision                                                            |
|------------------------|---------------------------------------------------------------------|
| Provider               | Google only                                                         |
| Platforms              | Android only (matches app.json + the eas.json APK profile)          |
| Library                | @react-native-google-signin/google-signin (free tier is enough)     |
| Runtime                | Development build required; Expo Go no longer covers auth paths     |
| Session model          | Verify Google idToken on the backend, then issue our own JWTs       |
| Access token lifetime  | 7 days                                                              |
| Refresh token lifetime | 90 days, rotated on every use, hash stored server-side so logout    |
|                        | can revoke it                                                       |
| Why 7 days             | The offline queue can sit for days; a long access token means most  |
|                        | queue drains need no refresh, and the refresh path covers the rest  |
| Token storage on phone | expo-secure-store (Android Keystore), never AsyncStorage            |
| userId value           | `User._id.toString()`                                               |
| Why that value         | Existing userId fields are already `String`, so CompletedWorkout,   |
|                        | TargetMuscle and CustomExercise need no type change                 |
| Existing 220 workouts  | Claimed by ADMIN_EMAIL via a one-off idempotent script (Phase 7)    |
| Onboarding fields      | Name, DOB, sex, height, weight, activity level, goal, diet          |
| Units                  | Stored metric (cm / kg); a toggle lets input be ft-in / lb          |
| Exercise catalog       | Stays global and unchanged; just moves behind the auth wall         |

Why our own JWT rather than passing the Google idToken on every request: Google idTokens
last about an hour and cannot be refreshed without a fresh native sign-in, which would
break the offline queue and force a sign-in prompt roughly hourly.

        email               String, required, unique, lowercase, trim
        name                String
        picture             String
        onboardingCompleted Boolean, default false
        profile:
          dateOfBirth       Date
          sex               enum ['male','female','other']
          heightCm          Number
          weightKg          Number
          activityLevel     enum ['sedentary','light','moderate','active','very_active']
          goal              enum ['cut','maintain','bulk']
          diet              enum ['veg','nonveg','eggetarian','vegan']
          unitPreference    enum ['metric','imperial'], default 'metric'
        refreshTokens: [{ tokenHash String, expiresAt Date, createdAt Date }]
        { timestamps: true }
      Keep `profile` fields optional - the document is created at sign-in, before onboarding.
- [ ] backend/constants/profile.js: export SEXES, ACTIVITY_LEVELS, GOALS, DIET_TYPES,
      UNIT_PREFERENCES. Follow the shape of backend/constants/muscles.js so the model and
      the validator share one source of truth.
- [ ] backend/services/tokenService.js:
        signAccessToken(user)   -> jwt, { sub: user._id.toString() }, 7d, JWT_ACCESS_SECRET
        issueRefreshToken(user) -> random 32 bytes hex; store sha256 hex in
                                   user.refreshTokens with expiresAt = now + 90d; return raw
        rotateRefreshToken(raw) -> look up by hash, reject if missing/expired, remove it,
                                   issue a new one; return { accessToken, refreshToken }
        revokeRefreshToken(raw) -> remove the matching hash
      Cap refreshTokens at 5 entries per user (drop oldest) and prune expired ones on write.
      Store only hashes - a leaked database dump must not yield usable refresh tokens.
- [ ] backend/services/googleVerifier.js: wrap `OAuth2Client.verifyIdToken` with
      `audience: [GOOGLE_WEB_CLIENT_ID, GOOGLE_ANDROID_CLIENT_ID].filter(Boolean)`.
      Reject the token unless `payload.email_verified === true`.
      Return { googleId: payload.sub, email, name, picture }.
- [ ] backend/controllers/authController.js:
        POST /api/auth/google   body { idToken }
          verify -> findOneAndUpdate by googleId (upsert, set email/name/picture)
          -> 200 { accessToken, refreshToken, user }
          -> 401 { error: 'invalid_google_token' } on verify failure
        POST /api/auth/refresh  body { refreshToken }
          -> 200 { accessToken, refreshToken }  (rotated)
          -> 401 { error: 'invalid_refresh_token' }
        POST /api/auth/logout   body { refreshToken }   -> 204
      Shape `user` once, in a `serializeUser` helper, and reuse it for /api/me.
      Never return refreshTokens, __v or _id-as-is; expose `id` as a string.
- [ ] backend/controllers/userController.js:
        GET /api/me            -> serialized user (includes onboardingCompleted + profile)
        PUT /api/me/profile    -> validate, save, set onboardingCompleted = true, return user
      Validation ranges (reject outside, do not clamp silently):
        dateOfBirth    a real date, age 13..100
        heightCm       100..250
        weightKg       30..300
        sex / activityLevel / goal / diet  must be in the enum
      Keep the computation of age / BMI / BMR / TDEE on the client. The server stores facts.
- [ ] backend/routes/authRoutes.js and backend/routes/userRoutes.js, following the shape of
      backend/routes/workoutRoutes.js.
- [ ] backend/middleware/auth.js - replace the stub entirely:
        read `Authorization: Bearer <token>`
        verify with JWT_ACCESS_SECRET
        on success: req.userId = payload.sub
        on missing/invalid/expired: 401 { error: 'unauthenticated' }
      Fail closed. Never set a fallback userId.
- [ ] server.js wiring order matters:
        app.use(cors()); app.use(express.json());
        app.get('/api/health', ...)              // public, no auth
        app.use('/api/auth', authRoutes);        // public, BEFORE app.use(auth)
        app.use(auth);                           // everything past here needs a token
        app.use('/api/me', userRoutes);
        app.use('/api/workouts', workoutRoutes);
        ... existing routes unchanged ...
        app.use(errorHandler);
- [ ] errorHandler currently returns 500 for everything. Give it a pass-through for errors
      carrying a `status`, so validation can answer 400 and auth can answer 401.

Done when, with curl against a local server:

Small phase, easy to skip, and skipping it is how data leaks between accounts.

        getTokens / setTokens / clearTokens over keys 'ff.access' and 'ff.refresh'.
      Every read in a try/catch returning null; SecureStore throws on some devices.
- [ ] src/services/authClient.ts - the single choke point for authenticated requests:
        authedFetch(url, init) =>
          attach Authorization: Bearer <access>
          if 401: await refreshOnce(); if that succeeded, retry the request exactly once
          if refresh failed: clear tokens, call the auth store's forceSignOut(), rethrow
      Deduplicate concurrent refreshes with a module-level in-flight promise, or a cold
      start with four parallel fetches will fire four refreshes and rotate the token out
      from under itself.
- [ ] src/services/api.ts:
        - `getJson` uses authedFetch instead of bare fetch.
        - `endpoints` gains: authGoogle, authRefresh, authLogout, me, meProfile.
        - add `api.getMe()` and `api.updateProfile(profile)`, with parsers in the same style
          as parseCompletedWorkout (dateOfBirth comes back as an ISO string - parse it to a
          Date here so no screen ever sees a string, per the file's own doc comment).
        - the auth and refresh calls must use bare fetch, not authedFetch, or they recurse.
- [ ] src/store/syncStore.ts - fix the drop-on-error behaviour:
        - route the request through authedFetch so queued writes carry a token
        - on 401 after a failed refresh: STOP draining and keep the queue (break, do not
          slice). The user is signed out; the work is not lost.
        - on 5xx: treat as retryable - break, keep the request.
        - on 4xx other than 401: current behaviour is right (log and drop).
      Without this, a workout finished while the token was stale is silently deleted.
- [ ] src/store/authStore.ts - zustand, user object persisted to AsyncStorage (tokens live
      in SecureStore, never here):

        user: User | null
        error: string | null
        hydrate()            read tokens; if present call api.getMe(); derive status from
                             user.onboardingCompleted; any failure -> signedOut
        signInWithGoogle()   hasPlayServices -> signIn -> POST /api/auth/google ->
                             setTokens -> set user + status
        completeOnboarding(profile)  PUT /api/me/profile -> set user, status 'ready'
        signOut()            see the data-isolation step in Phase 5
        forceSignOut()       token-expiry path: same as signOut but no server call
      Map the native error codes to human text: SIGN_IN_CANCELLED -> no error shown at all,

## Phase 7 - Claim the 220 existing workouts

Runs last. It needs your User document to exist, which means you must have signed in through
the finished app at least once.

- [ ] Back up first. The repo already has fitfreak_complete_backup.json (2026-10-29) as
      precedent, but take a fresh one:
        mongodump --uri "$MONGO_URI" --out ./backup-pre-auth-$(date +%F)
      Do not count on the committed JSON file; it is two weeks stale.
- [ ] backend/scripts/claimDefaultUser.js:
        - reads ADMIN_EMAIL, finds that User; exits with a clear message if absent
          ("sign in through the app first")
        - counts documents with userId 'default_user' in CompletedWorkout, TargetMuscle and
          CustomExercise and prints the counts
        - with `--dry-run` (the default): prints what it would change and exits
        - with `--commit`: updateMany userId 'default_user' -> user._id.toString() in all
          three collections, then re-counts and prints the result
        - idempotent: a second run finds zero and exits cleanly
