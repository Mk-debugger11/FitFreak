# FitFreak - Nutrition Tab (maintenance calories, meal logging, energy balance)

Status: not started (written 2026-11-13).
Work through the phases in order. Phase 4 can run alongside Phase 3, and Phase 2 can run
alongside Phase 1 once the types in 1a exist. Tick the [ ] boxes as work lands; each phase ends
with a "Done when" check.


## Goal

- A third bottom tab, "Nutrition", showing one day at a time (same date strip as the Workout
  tab).
- The user's maintenance calories, computed from a formula (Mifflin-St Jeor BMR x activity
  multiplier) using a profile they fill in once.
- Meals logged into four parts of the day: Breakfast, Lunch, Snacks, Dinner. Each meal lists its
  entries and its own macro totals.
- A day total: calories plus protein / carbs / fat.
- An energy-balance verdict against maintenance: Deficit, Maintenance, or Surplus, with the
  signed difference in kcal.


## Starting point

- Two bottom tabs (Home, Workout) wired in `src/core/Navigation.tsx`, with a global
  `ActiveWorkoutSheet` and a `MinimizedWorkoutBar` rendered above the tab bar. A third tab drops
  in next to them; nothing about the sheet changes.
- There is NO user profile anywhere in the app. `grep -ri "profile\|heightCm\|birth" src backend`
  finds nothing but unrelated hits. Height, weight, age, sex and activity level all have to be
  introduced - this is the one genuinely new concept in the feature, and the maintenance number
  cannot be computed without it.
- `src/components/HorizontalCalendar.tsx` already gives a date strip (365 days back, 1 forward,
  future dates disabled). The Nutrition screen reuses it as-is.
- `src/components/ModalSheet.tsx` (+ `ModalOption`, `ModalEmptyText`), `Button`, `Card`, `Chip`,
  `Input` and `SegmentedControl` cover every dialog and control this feature needs. No new
  shared component is required except a macro bar, which is nutrition-specific and therefore
  lives in the feature folder, not `src/components/`.
- The offline-first pattern is fixed and must be followed: local state first, then
  `enqueueSync(url, method, body)`. Reads go through `api.*`, which is the only module that
  knows URLs or converts ISO strings to `Date`.
- `historyStore.ts` is already large (fetch windows, merge-by-id, migration-on-rehydrate).
  Nutrition gets its own stores rather than being bolted onto it.
- The exercise catalogue shows the pattern to copy for a food catalogue: split JSON under
  `src/constants/exerciseCatalog/`, a byte-parity copy at `backend/data/exerciseCatalog.json`,
  lazy seeding in the controller (`ensureExercisesSeeded`), a parity checker in
  `scripts/validateCatalog.mjs`, and a client read that tolerates a 404 from an older server
  (`api.getExercises()` returns `null`).
- Tests are `node:test` files in `tests/` that compile the TypeScript under test on the fly
  (see `tests/scoringEngine.test.mjs`). The pure nutrition maths gets the same treatment.


## Decisions

| Topic                   | Decision                                                              |
|-------------------------|-----------------------------------------------------------------------|
| Maintenance formula     | Mifflin-St Jeor BMR x activity multiplier (TDEE)                      |
| Second formula          | Katch-McArdle when body fat % is filled in (optional, more accurate)  |
| Manual escape hatch     | `maintenanceOverride` on the profile wins over any computed value     |
| Age                     | Store `birthDate`, derive age, so the number never goes stale         |
| Parts of day            | Exactly four: breakfast, lunch, snacks, dinner (fixed, not editable)  |
| Day bucket              | Local `YYYY-MM-DD` `dateString`, like target muscles - not an ISO range |
| Food macro basis        | per 100 g / per 100 ml / per piece, plus named servings (e.g. "1 roti") |
| Entry macros            | Snapshotted onto the entry at log time, never re-derived from the food |
| Calories of a food      | Stored explicitly; derived from 4/4/9 only when missing from the data |
| Verdict band            | Within +/- max(100 kcal, 5% of maintenance) counts as Maintenance     |
| Empty day               | No entries = no verdict (not "deficit"); show a prompt instead        |
| Exercise calories       | NOT subtracted in v1. Maintenance already includes an activity factor |
| Backend                 | New: foods, custom foods, nutrition entries, profile                  |
| Where state lives       | Two new stores: `nutritionStore.ts` and `profileStore.ts`             |

- [ ] interface MacroNutrients { calories: number; protein: number; carbs: number; fat: number; }

      for a logged entry's snapshot, for a meal subtotal and for a day total.
- [ ] interface FoodServing { label: string; grams: number; }
      A named portion ("1 medium roti", 45). `grams` is in the food's basis unit (g, ml or
      pieces), so a per_piece food's serving is `{ label: '2 eggs', grams: 2 }`.
- [ ] interface FoodItem {
        name: string;
        aliases?: readonly string[];
        category: FoodCategory;        // see 1c
        basis: FoodBasis;
        macros: MacroNutrients;        // the values AT that basis (per 100 g / 100 ml / piece)
        servings?: readonly FoodServing[];

        notes?: string;
      }
- [ ] interface CustomFood extends FoodItem { id: string }
      User-created foods carry an id so they can be deleted; catalogue foods are keyed by name.
- [ ] interface LoggedFood extends Entity {
        dateString: string;            // local YYYY-MM-DD

        foodName: string;              // denormalized, survives a food being renamed/deleted

        quantity: number;              // in basis units: grams, ml, or pieces
        servingLabel?: string;         // what the user picked, for display ("2 rotis")
        macros: MacroNutrients;        // SNAPSHOT for `quantity`, already scaled
        foodId?: string;               // custom food reference, when there was one
        loggedAt: Date;                // time of day, for ordering inside a meal
      }
- [ ] interface UserProfile extends Entity {
        sex: Sex;
        heightCm: number;
        weightKg: number;
        birthDate: Date;
        activityLevel: ActivityLevel;
        goal: NutritionGoal;

## Phase 2 - The maths (pure functions + tests, no React, no store)

All of this is pure and unit-tested before any UI exists, exactly as
`src/features/home/muscleActivity.ts` was.

2a. `src/features/nutrition/energyFormulas.ts` - new

- [ ] mifflinStJeorBmr({ sex, weightKg, heightCm, ageYears }): number
        male:   10*weightKg + 6.25*heightCm - 5*ageYears + 5
        female: 10*weightKg + 6.25*heightCm - 5*ageYears - 161
- [ ] katchMcArdleBmr({ weightKg, bodyFatPercent }): number
        leanMass = weightKg * (1 - bodyFatPercent/100); bmr = 370 + 21.6 * leanMass
- [ ] computeBmr(profile): { kcal: number; formula: 'mifflin_st_jeor' | 'katch_mcardle' } | null
      Uses Katch-McArdle when `bodyFatPercent` is a sane number (3-60), else Mifflin-St Jeor.
      Returns null when the profile is missing or any required field is out of range, so callers
      must handle "unknown" rather than render a wrong number. The returned `formula` is what the
      profile sheet names on screen.
- [ ] computeMaintenanceCalories(profile): { kcal, bmr, multiplier, formula, isOverride } | null
      `maintenanceOverride` short-circuits everything and comes back with `isOverride: true`.
      Otherwise kcal = round(bmr * ACTIVITY_MULTIPLIERS[activityLevel]).
- [ ] computeCalorieTarget(profile): number | null
      maintenance + GOAL_ADJUSTMENTS[goal], floored at 1200 so a cut never suggests something
      unsafe.
- [ ] computeMacroTargets(profile): MacroNutrients | null
        protein g = round(weightKg * (proteinPerKg ?? DEFAULT_PROTEIN_PER_KG))
        fat g     = round(target * DEFAULT_FAT_CALORIE_SHARE / 9)
        carbs g   = round(remaining kcal / 4), floored at 0
      Guard the degenerate case where protein + fat already exceed the target (very low target,
      very heavy user): scale protein and fat down proportionally rather than returning negative
      carbs.
- [ ] Validation ranges in one place (PROFILE_LIMITS): weightKg 25-300, heightCm 100-250,
      age 13-100, bodyFatPercent 3-60. Used by both these functions and the profile form, so
      the form and the maths can never disagree.

2b. `src/features/nutrition/energyBalance.ts` - new

- [ ] export type EnergyBalanceStatus = 'deficit' | 'maintenance' | 'surplus';
- [ ] classifyEnergyBalance(intakeKcal, maintenanceKcal, { hasEntries }):
        { status: EnergyBalanceStatus; deltaKcal: number; toleranceKcal: number } | null
      Returns null when `maintenanceKcal` is null/0 (no profile yet) OR when `hasEntries` is
      false - a day with nothing logged is not a 2000 kcal deficit, it is an unfilled day. This
      is the single most important edge case in the feature; the screen shows a prompt instead
      of a verdict in both cases.
      tolerance = max(MAINTENANCE_BAND.minKcal, maintenance * MAINTENANCE_BAND.fraction)
        delta = intake - maintenance
        |delta| <= tolerance -> 'maintenance'; delta < 0 -> 'deficit'; else 'surplus'
- [ ] STATUS_LABELS: Record<EnergyBalanceStatus, string> = Deficit / Maintenance / Surplus and
      statusColor(status) reading `theme.colors.nutrition`.

2c. `src/features/nutrition/servingMath.ts` - new

- [ ] caloriesFromMacros(macros): number - 4/4/9, for foods whose data omits calories.
- [ ] scaleMacros(food, quantity): MacroNutrients
      quantity is in basis units; divide by BASIS_UNITS[basis].amount and multiply. Keeps full
      float precision - rounding happens only at display time.
- [ ] addMacros(a, b) and emptyMacros() - the accumulators the totals module folds with.
- [ ] macroCalorieShares(macros): { protein: number; carbs: number; fat: number }
      Each macro's share of the kcal it accounts for, normalized to sum to 1 (0/0/0 when the
      entry is empty). This is what drives the stacked macro bar, so the bar stays honest even
      when a food's stored calories disagree slightly with 4/4/9.

2d. `src/features/nutrition/nutritionTotals.ts` - new

- [ ] computeDayNutrition(entries: LoggedFood[], dateKey: string) returns:
        {
          byMeal: Record<MealType, { entries: LoggedFood[]; totals: MacroNutrients }>,
          totals: MacroNutrients,
          entryCount: number,
        }
      Rules: keep only entries whose `dateString === dateKey`; order each meal's entries by
      `loggedAt` ascending; every MealType key is always present (empty array + zero totals), so
      the screen can render four sections without null checks.
- [ ] computeRemaining(totals, target): { kcal: number; isOver: boolean } for the "N left" line.

2e. Tests

- [ ] `tests/energyFormulas.test.mjs` - copy the compile harness from
      `tests/scoringEngine.test.mjs`. Cover:
        - Mifflin-St Jeor against hand-worked values for a male and a female profile.
        - Katch-McArdle taking over when bodyFatPercent is set, and being ignored at 0 or 80.
        - every ACTIVITY_MULTIPLIERS rung.
        - `maintenanceOverride` beating the formula.
        - null for an incomplete or out-of-range profile.
        - computeMacroTargets summing to the target within rounding, and the degenerate
          low-target case not producing negative carbs.
- [ ] `tests/nutritionBalance.test.mjs` - cover:
        - deficit / maintenance / surplus either side of the band, and exactly ON the band edge.
        - null with no profile, and null with a profile but zero entries.
        - computeDayNutrition bucketing four meals, ignoring other dates, ordering by loggedAt,
          and summing macros; scaleMacros for all three bases and for a named serving.
- [ ] Both files runnable with `node --test tests/`.

Done when: `node --test tests/` passes (new files included) and `npm run typecheck` is clean.

## Phase 5 - Nutrition log store and its endpoint

5a. Backend entries

- [ ] `backend/models/LoggedFood.js` - userId, id (client-generated, unique), dateString,
      mealType (enum), foodName, basis, quantity, servingLabel, macros (nested), foodId,
      loggedAt, timestamps. Compound index on (userId, dateString) - every read is "one day" or
      "a range of days".
- [ ] `backend/controllers/nutritionController.js`:
        getEntries   - `?startDate=&endDate=` as `YYYY-MM-DD` strings, compared
                       lexicographically (`$gte`/`$lte`), sorted by dateString then loggedAt.
                       Range-by-dateString is the whole reason entries are keyed this way:
                       an ISO instant range, like `/workouts` uses, splits a day across
                       timezones and would make the day total wrong near midnight.
        addEntry     - validate mealType and dateString shape, sanitizeMacros, upsert on `id`
                       so a replayed offline POST is idempotent.
        updateEntry  - PUT `/:id`, accepts quantity + macros + mealType (the serving dialog can
                       edit an existing row).
        deleteEntry  - DELETE `/:id`.
- [ ] `backend/routes/nutritionRoutes.js` and `/api/nutrition-entries` in `server.js`.

5b. `src/store/nutritionStore.ts` - new

- [ ] State:
        isLoading, isFetching, hasHydrated
        loggedFoods: LoggedFood[]            // flat, newest day first
        foodsCatalog: FoodItem[]             // server catalogue, falls back to builtins
        customFoods: CustomFood[]
        fetchedNutritionDates: Record<string, boolean>
- [ ] Actions:
        fetchNutritionData()        - cold start: entries for the last 7 days (reuse
                                      INITIAL_HISTORY_DAYS' value via a local
                                      INITIAL_NUTRITION_DAYS), foods, custom foods, in a single
                                      `Promise.allSettled`, each failure logged but not fatal -
                                      the exact shape of `historyStore.fetchData`.
        fetchEntriesForDate(date)   - guarded by `fetchedNutritionDates` and an
                                      `inFlightDateFetches` map, like
                                      `fetchWorkoutsForDate`.
        logFood(input)              - build the LoggedFood (createId, loggedAt, snapshot macros
                                      via scaleMacros), prepend locally, then
                                      `enqueueSync(endpoints.nutritionEntries, 'POST', entry)`.
        updateLoggedFood(id, patch) - re-scale the snapshot, patch locally, PUT.
        deleteLoggedFood(id)        - filter locally, DELETE.
        addCustomFood(food)         - createId, append locally, POST. Reject a name that already
                                      exists (normalized), returning false so the modal can show
                                      an error.
        deleteCustomFood(id)        - local filter + DELETE. Past entries are untouched: they
                                      hold their own macro snapshot and their own `foodName`.
- [ ] Derived selector `searchFoods(query)`: merges `customFoods` first, then `foodsCatalog`
      (or ALL_BUILTIN_FOODS when the catalogue is empty), matching name and aliases
      case-insensitively, prefix matches ranked above substring matches, capped at 50 results.
- [ ] Derived selector `recentFoods(limit = 8)`: distinct `foodName`s from the newest entries,
      so re-logging a usual breakfast is two taps.
- [ ] Persist as "nutrition-storage" with `partialize` over loggedFoods / foodsCatalog /
      customFoods / fetchedNutritionDates and a `merge` that revives dates through
      `parseLoggedFood` and drops malformed rows, mirroring `historyStore`'s merge.
