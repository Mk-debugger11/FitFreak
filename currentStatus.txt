FITFREAK - CURRENT STATUS
Last updated: 2026-11-14

A React Native (Expo) workout tracker and nutrition tracker with an Express + MongoDB backend.
Three bottom tabs:
  - Home (`src/features/home/HomeScreen.tsx`): interactive 3D muscle anatomy
    heat map with daily/weekly training intensity and per-muscle breakdowns.
  - Nutrition (`src/features/nutrition/NutritionScreen.tsx`): daily meal logging
    (Breakfast, Lunch, Snacks, Dinner), macro breakdown, energy balance against
    maintenance calories (Mifflin-St Jeor / Katch-McArdle) and goal targets.
  - Workout (`src/core/WorkoutTab.tsx`): workout log and active workout logger
    (one workout = one exercise, logged against a day and target muscle group),
    with an active-workout indicator dot on the Workout tab icon.

Stack: Expo SDK 56 (expo ~56.0.11) / React Native 0.85.3 / React 19.2.3 /
TypeScript ~6.0.3 / Zustand ^5.0.14 / React Navigation 7 (@react-navigation/native
^7.2.5, bottom-tabs ^7.16.2, native-stack ^7.16.0) / AsyncStorage 2.2.0 /
NetInfo 12.0.1 / lucide-react-native ^1.17.0.
3D stack: three ^0.187.0 / @types/three ^0.187.0 (dev) / @react-three/fiber
^9.8.2 / @react-three/drei ^10.7.9 / expo-gl ~56.0.6 / expo-file-system
~56.0.11 / expo-asset ~56.0.25.

4. CODE FLOW
================================================================================

--- 4.1 Cold start ---------------------------------------------------------------

  index.ts
    -> imports src/core/threePolyfills (FinalizationRegistry / WeakRef shims)
    -> src/core/App.tsx mounts
    -> AsyncStorage rehydrates historyStore and syncStore in the background.
       On rehydrate, dates are parsed back from ISO strings and isLoading is
       cleared, so cached data paints immediately.
    -> App's useEffect calls historyStore.fetchData():
         drains syncStore queue, then api.getWorkouts(last 7 days) +
         api.getTargetMuscles() + api.getCustomExercises() in parallel.
       Results are merged by id (never duplicated) and the last 8 date keys are
       marked as fetched.
    -> App shows the spinner until isLoading clears - which rehydration does
       as soon as storage has been read, and fetchData does when it settles.
       fetchData only keeps it up when there was nothing cached to show.
    -> Then: SafeAreaProvider > NetworkListener + RootNavigator > Home tab
       (HomeScreen) as the initial tab, alongside the Workout tab (WorkoutTab).

--- 4.2 Home 3D muscle map & activity --------------------------------------------

  HomeScreen
    -> useMuscleActivity(period) selects completedWorkouts from historyStore,
       anchors today / Monday-Sunday range (refreshing on focus via
       useFocusEffect), and calls computeMuscleActivity().
    -> BodyViewer mounts <Canvas frameloop="demand"> with OrbitControls and
       BodyModel. BodyModel loads `assets/models/body.glb` via useGLTF, resolves
       each mesh's `userData.label` via `resolveAnatomyMuscleId`, assigns
       `theme.colors.anatomy` materials by intensity/selection, and calls
       `invalidate()`.
    -> Switching Daily/Weekly updates scores and recolors meshes; tapping
       Front/Back animates `rotation.y` (`0` <-> `Math.PI`) and resets
       OrbitControls.
    -> Tapping a muscle mesh or worked-muscle chip sets `selectedMuscle` and
       opens `MuscleDetailSheet`; tapping the info icon opens the
       `"Anatomy Model Credits"` modal; an active workout shows a shortcut
       banner to jump to the Workout tab.

--- 4.3 Moving between days (Workout tab) ----------------------------------------

  HorizontalCalendar.onSelectDate
    -> WorkoutLogScreen setSelectedDate
    -> effect 1 clears the category filter (it belonged to the old day)
    -> effect 2: if that date has not been fetched (and isn't already covered by
       an in-flight initial fetch), show the inline spinner and call
       historyStore.fetchWorkoutsForDate(date) -> api.getWorkouts(day range)
       -> merge + mark the date fetched
    -> the day's workouts are recomputed (filter by day, then by category,
       then sorted) and rendered as WorkoutCards.

  Past days are read-only: no New button, no delete, no chip editing.

--- 4.4 Setting target muscles ---------------------------------------------------

  TargetMuscleBar search -> pick a suggestion
    -> WorkoutLogScreen -> historyStore.addTargetMuscleGroup(localDateKey, group)
    -> local state updates at once, then enqueueSync(POST /target-muscles)
    -> the chip appears; removing one mirrors this with DELETE.

--- 4.5 Starting and logging a workout -------------------------------------------

  "New" -> CategoryPickerModal (the day's target muscles, or Mixed/Other)
        -> ExercisePickerModal (catalogue + custom for that category)
           -> pick one, OR "+ Create Custom Exercise" -> CustomExerciseModal
              (name + equipment; also saves it via historyStore.addCustomExercise)
        -> activeWorkoutStore.startWorkout(name, { startTime: selectedDate,
           category, equipmentType })

  currentWorkout is now set, so WorkoutTab swaps WorkoutLogScreen for
  ActiveWorkoutScreen (and the Workout tab icon shows an active indicator dot,
  while HomeScreen shows a "Workout in progress - Continue" banner):
    AddSetForm      -> addSet(weight, reps)
    SetRow          -> updateSet / toggleSetComplete / deleteSet
    name field      -> updateWorkoutName; on blur, addCustomExercise
    Cancel          -> cancelWorkout (discarded, nothing is saved)
    Finish          -> finishWorkout() stamps endTime and clears the store,
                       then historyStore.addCompletedWorkout(workout):
                         - totals computed from completed sets only
                         - prepended to completedWorkouts
                         - enqueueSync(POST /workouts)
                       WorkoutTab falls back to WorkoutLogScreen, and HomeScreen's
                       useMuscleActivity recomputes automatically.

--- 4.6 Offline sync -------------------------------------------------------------

  Every mutation follows the same path: update local state, then
  enqueueSync(url, method, body).

  enqueueRequest appends to the persisted queue and immediately asks NetInfo
  whether it is online; if so it calls processQueue().

  processQueue drains the queue one request at a time:
    - HTTP response (even 4xx/5xx): log if not ok, drop the request, continue.
      Retrying a rejected request would never succeed.
    - Network failure: stop, keep the request and everything behind it.

  NetworkListener re-runs processQueue on every reconnect (and retries initial
  fetchData if `hasSyncedFromServer` is false), so the app is usable offline and
  catches up on its own.

--- 4.8 Logging a meal and tracking nutrition -----------------------------------

  NutritionScreen
    -> reads user profile from `profileStore` (or prompts to setup if null)
    -> selectedDate drives `useDayNutrition(dateKey)`
    -> `CalorieSummaryCard` displays consumed calories, maintenance, remaining kcal vs target,
       and Deficit / Maintenance / Surplus pill (+/- 5%, min 100 kcal band)
    -> `MacroTotalsBar` shows stacked bar (shares) + 3 macro target chips
    -> four `MealSection`s (Breakfast, Lunch, Snacks, Dinner):
       "+" / empty row -> `FoodPickerModal`
       - search food catalog or recent foods, or "+ Create custom food" -> `CustomFoodModal`
       - selecting food opens `ServingModal` with live scaled macros preview
       - "Add to Meal" -> `nutritionStore.logFood(...)`: snapshots macros via `scaleMacros`,
         prepends locally, enqueues sync to `POST /api/nutrition-entries`.
       - tapping entry opens `ServingModal` to edit portion (`PUT /api/nutrition-entries/:id`)
       - delete icon deletes entry locally and enqueues `DELETE /api/nutrition-entries/:id`.
       - past day edits/deletes are allowed; future dates disable adding.

5. CONVENTIONS
================================================================================

  - Global state lives in src/store/. Screens hold only UI state.
  - Only src/services/api.ts knows URLs, HTTP or the wire format.
  - Only that file converts strings to Dates; the rest of the app sees Dates.
  - Reads go through api.*; writes go through enqueueSync, never fetch directly.
  - No colours, spacings or font weights outside src/theme.ts (including
    `theme.colors.anatomy`).
  - Shared UI in src/components/ (no store imports). Feature components take
    props only - the screen owns store subscriptions.
  - Target-muscle and fetched-date keys both use local `YYYY-MM-DD`
    (`toLocalDateKey` / `toFetchKey`), while workout API range queries send
    Date boundaries serialized as ISO strings.

  Where to add things:
    a new screen        -> src/features/<feature>/, route it in core/Navigation
    a new shared widget -> src/components/ + export it from index.ts
    a new endpoint      -> src/services/api.ts, then the store that needs it
    a new exercise      -> src/constants/exercises.ts (with primary/secondary
                           muscles)
    a muscle mapping    -> src/constants/muscles.ts & src/constants/anatomyMap.ts


================================================================================
6. KNOWN GAPS
================================================================================

  - Backend is still JavaScript; its model definitions duplicate src/types.ts.
  - Nutrition constants duplicate across `src/constants/nutrition.ts` and `backend/constants/nutrition.js`, mirroring the muscle constants pattern.
  - Automated test coverage exists for pure math, nutrition balance, catalog parity, and client stores (`node --test tests/*.test.mjs`).
  - Single user, hard-coded ('default_user'). No auth.
  - An in-progress workout is not persisted - killing the app loses it.
  - Elapsed time on the active workout is computed on render, so it only
    advances when something else re-renders the screen.
  - Phase 6 optional extras from `implementation_plan_homepage.txt` (past-day/
    week arrows, lighting up in-progress sets, per-exercise muscle picking for
    custom exercises, target-muscle outlines, smooth color fades) are not yet
    implemented; custom or renamed exercises fall back to category-level muscles.
  - Failed syncs are dropped after logging; there is no retry or error surface
    in the UI.
